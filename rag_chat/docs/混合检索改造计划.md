## Context（为什么做）

当前检索是纯 ChromaDB 向量（余弦）top8 → 去重 → 同文档补块。Q3 类问题暴露短板：**"报名截止时间"这类关键词精确命中的信息，纯向量语义检索经常捞不到**（关键句埋在文档中段、与 query 语义重叠度低）。

目标：把项目做得更工程化 —— 加入 **BM25 关键词召回 + RRF 融合**（补关键词短板），重排做成可开关组件；然后跑**消融实验**对比三档，用数据证明每个组件的价值（毕业论文的工程证据）。

Qwen 评分器**不作为本改造的验收目标**——只验证功能正确 + 检索质量提升（用户已确认）。

**路线确认**：本次做 ① 混合检索改造 ② 消融实验，这两个是剩余核心步骤；MCP 同步 / README 更新为可选后续。

## 改造范围

- 只改主链路 `app_backend.py` 的 `_search_knowledge_base`（AgentLoop / 网页 / 评测都走它）。
- MCP 工具（`mcp_server/tools.py`）是独立链路，本次不动，后续可选同步。

## 依赖现状

- 已装 `sentence-transformers` / `torch` / `transformers` → 重排直接用其 `CrossEncoder`，**不新增依赖**。
- 缺 `jieba`、`rank-bm25` → 两个纯 Python 小包，新增无压力。
- 库：`my_rag_collection` 6432 块 / 1121 篇 / 13 分类，元数据含 source/category/year/url。

## 实施步骤

### Step 1：加依赖
- `pip install jieba rank-bm25`
- **功能**：jieba 做中文分词（BM25 必需），rank_bm25 提供 OKAPI BM25 打分。
- **为什么**：轻量纯 Python 包，不引入重型依赖。
- 实施：`jieba 0.42.1` + `rank_bm25 0.2.2`，✅

### Step 2：新建 `src/hybrid_retriever.py`（三件套组件，全部惰性 + 模块级单例缓存）
- `Bm25Retriever`：
  - 启动懒加载全量块（`collection.get()`，6432 块），jieba 分词建倒排索引。
  - `search(query, top_n, year=None)`：分词 query → 全库打分 → 取 top30 → 按 year 过滤 → 取 top_n；返回 `{text, metadata, distance}`，distance 用归一化 BM25 分换算（保持与现有"相似度%"展示格式一致）。
- `rrf_fuse(vector_results, bm25_results, k=60, top_n)`：Reciprocal Rank Fusion 融合两路，无权重参数，稳健。
- `Reranker`（可选开关）：
  - `load()` 懒加载 `sentence_transformers.CrossEncoder`（multilingual 小模型 ~100MB），仅开关开启时才下载/加载。
  - `rerank(query, candidates, top_n)`：对 `(query, text)` 对打分重排。
- **功能**：检索三件套解耦，聊天链路只加载用到的部分，重排开关不影响其他环节。
- 实施：✅（重排模型 `BAAI/bge-reranker-base`，中文精排标准选择，hf-mirror 可下载；
  原计划用 `mmarco-mMiniLMv2-L6-H384`，镜像 404 不可用，改为 bge-reranker-base）

### Step 3：改 `_search_knowledge_base`（app_backend.py）
新流程（保留现有环节，插入融合 + 可选重排）：
1. 库外闸门（不变）
2. 年份过滤（向量 `where` 不变；BM25 在候选里按 year 过滤）
3. 向量召回 top_k + **BM25 召回 top_k（新增）**
4. **RRF 融合** → 取融合 top_k（默认 8）
5. 文本去重（现有逻辑）
6. 同文档补块（现有逻辑，保留）
7. `RETRIEVAL_RERANK=on` 时：对去重后候选重排再截断
8. 格式化（**格式不变**，兼容 `_parse_sources` 正则；显示相似度取该块两路中的最高分）

新增 `.env` 开关（加到 `.env.example`）：
- `RETRIEVAL_MODE`：`hybrid`（默认）| `vector`（退纯向量，消融对照）
- `RETRIEVAL_RERANK`：`on`/`off`（默认 off）
- `RERANK_TOP_N`：重排候选数（默认 8）
- **鲁棒性**：jieba/rank_bm25 导入失败或 BM25 构建失败 → 自动回退纯向量，打日志不崩。

- **功能**：混合检索成为主链路默认，可一键开关对比。
- **为什么**：所有环节在既有链路内串起来，输出格式不变则前端来源解析（`_parse_sources`）不破。
- 实施：✅

### Step 4：混合检索消融实验
- 复用基准 6 题 + `run_one`，加 `--mode` 参数：
  - `vector`：纯向量（当前基线）
  - `hybrid`：向量 + BM25 RRF
  - `hybrid_rerank`：融合 + 重排
- 每档输出 `eval_results_hybrid_{mode}.json`（已随项目清理删除，成绩存档见 [改进记录.md](改进记录.md)）。
- **检索质量证据**：每题记录关键句是否命中（Q3"报名截止/6月24日"、Q5"3月3-15/台账"），落盘供对比。
- **功能**：三档数据对比，量化每个组件的贡献。
- **为什么**：毕业论文需要"为什么加 BM25 / 为什么加重排"的数据支撑。
- 实施：✅

## 验证（验收标准）

1. 冒烟：`Bm25Retriever().search("报名截止", 5)` 命中 Q3 文档"学院初赛6月24日"块。
2. 检索级：Q3 的 BM25 召回命中关键块；Q5 融合后排查通知仍在候选。
3. 端到端：消融脚本三档各跑 6 题，对比 Q3/Q5 关键句命中率与答案。
4. 回归：hybrid 档 Q1-Q6 不劣于纯向量档（检索来源/答案质量不下降）。
5. 格式不破：网页聊天来源解析正常。

## 实施结果（2026-08-08）

| 验证项 | 结果 |
|---|---|
| 冒烟：BM25 命中 Q3 目标文档 | ✅ 完整 Q3 query 下第 1/5 位均命中"中国国际大学生创新大赛校赛通知"，第 5 位块含 `6月24日`/`6月10日` |
| 检索级：hybrid 端到端（不走 LLM） | ✅ Q3 最终上下文含 6月24日+6月10日；来源解析 16 条，格式兼容 `_parse_sources` |
| 端到端：hybrid 档 6 题 | ✅ Q3 检索命中 `[报名截止, 6月24日, 6月10日]`、Q5 检索命中 `[3月3日, 3月15日, 3月20日, 台账]` |
| 三档对比 | ✅ hybrid 档 6/6 满分（60/60），详见 [改进记录.md](改进记录.md) |
| 重排模型 | `BAAI/bge-reranker-base`（~440MB，hf-mirror 可下载）；mmarco 小模型镜像 404 不可用，已换 |
| BM25 独立价值 | 探测 8 条关键词查询：BM25 均引入向量漏掉的来源，如"转专业"→《智能工程学院2025级普通本科生转专业工作实施细则》 |

### 三档关键句命中（Q3 总 3 句 / Q5 总 4 句，检索级）

| 模式 | Q3 检索级 | Q5 检索级 | 说明 |
|---|---|---|---|
| vector（基线） | 2/3 | 4/4 | 缺"报名截止"字面（片段截断 800 字） |
| hybrid | 3/3 | 4/4 | 两路融合，Q3 补上字面命中 |
| hybrid_rerank（N=8） | 3/3 | 0/4 | 重排截断到 8 条，把埋在补块里的关键句挤掉 |
| hybrid_rerank（N=16） | 3/3 | 4/4 | 重排只排序不牺牲召回，推荐配置 |

**结论（如实记录）**：
1. 对本基准 6 题，关键句命中已被"同文档补块"覆盖，三档（vector/hybrid/rerank-N16）在 Q3/Q5 上检索级命中均接近饱和（Q3 仅 vector 少"报名截止"字面，hybrid 补上）。
2. BM25+RRF 的增量体现在**对向量初始召回漏掉的文档的补充**（如转专业、寒假管理通知等）——对"关键词精确命中但语义重叠低"的查询更具鲁棒性，这是混合检索的理论价值与论文定位。
3. **重排发现**：RERANK_TOP_N=8 会截掉宽泛题（如 Q5「有哪些安排」）埋在补块里的关键句；N=16 时重排只优化排序不牺牲召回。默认值已设为 16。
