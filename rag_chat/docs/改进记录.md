## 2026-08-08 ｜ 批次 1：检索质量加固（纯向量链路）

### 1. 库外主体校验闸门（`_refuse_out_of_kb_school`）
- **改了什么**：识别 query 中的学校名（正则「XX大学/XX学院」+ 泛指字过滤），问知识库主体（河南工学院）之外的学校 → 直接拒答，不进检索。
- **为什么**：Q6「河北工学院录取分数线」——库外题若强行检索，LLM 会把主体校分数张冠李戴，编造幻觉数字。
- **效果**：Q6 从 0 分（幻觉）修复到 10 分（正确拒答）。

### 2. 年份过滤（`_extract_year` + Chroma `where={"year": year}`）
- **改了什么**：query 提到 20xx 年份 → 检索时按元数据 year 过滤，只看该年文档。
- **为什么**：跨年旧通知（如 2025 年心理健康工作）会挤占检索名额，污染当年答案。
- **效果**：清除跨年污染，当年通知稳占候选。

### 3. 文本去重（seen set）
- **改了什么**：检索结果按文本内容去重。
- **为什么**：同一通知被爬进两个分类目录 + 重叠窗口 → 产生内容相同的块，重复占名额。
- **效果**：候选不重复，名额留给不同文档。

### 4. 同文档补块（按 source 元数据整篇补齐）
- **改了什么**：对初始命中的每个来源，用 `collection.get(where={"source": src})` 拉该文档全部块，追加未召回的后续块（每来源限补 3 块、最多补 5 篇、总封顶 TOP_K+12=20）。
- **为什么**：宽泛问题（如 Q5「有哪些安排」）常只命中文档开头，关键句（3月3-15日排查、3月20日台账）埋在正文第二、三节，语义相似度捞不到。
- **效果**：Q5 排查通知（2026-03-03）关键事实稳定进上下文（3/3 可靠命中）。

### 5. 综合通知优先提示词（SYSTEM_PROMPT 第 10 条）
- **改了什么**：问「有哪些安排/如何开展/工作怎么做」类概括题时，以覆盖多项工作的综合性通知（标题常含「有关工作的通知」）为作答主干，完整列出各项工作及日期要求。
- **为什么**：Q5 检索到综合通知+单次活动通知时，LLM 按显示相关度锚定到单次《测评通知》（3月11-27），漏掉综合《排查通知》（3月3-15 排查 / 3月20 台账）——非确定性问题，1/3 概率答对。
- **效果**：Q5 可靠性提升到 3/3。

### 6. Q6 拒绝消息强化
- **改了什么**：拒绝文案明确「严禁补充河南工学院或其他学校的任何信息（含录取分数），即使作为附加说明也不行，只拒绝不展开」。
- **为什么**：回归测试发现补块逻辑把录取分数线文档带进上下文，LLM 列出河南工学院分数（531/520）——违反基准表外数字即幻觉的规则。
- **效果**：Q6 稳定拒答，不越界补充。

## 2026-08-08 ｜ 批次 2：混合检索改造（BM25 + RRF + 可选重排）

### 背景
纯向量语义检索对"关键词精确命中"类信息（如 Q3「报名截止时间」）鲁棒性不足：关键句埋在文档中段、与 query 语义重叠度低时，余弦相似度经常捞不到。

### 施工前的方案（原《混合检索改造计划》存档，2026-08-08）

> 计划书原件已并入本条，独立文件已删除——两处内容重复（最刺眼的是那张三档命中表逐字出现两遍），
> 改一处漏一处迟早打架，而论文需要的是「计划 → 实施 → 结果」一条线，不是两份并行。

- **目标**：把检索链路做得更工程化——加 **BM25 关键词召回 + RRF 融合**补关键词短板，重排做成**可开关组件**；再跑**消融实验**对比三档，用数据证明每个组件的价值（论文的工程证据）。
- **验收口径**：Qwen 评分器**不作为本改造的验收目标**，只验证「检索功能正确 + 检索质量提升」（用户确认）。
- **范围**：只改主链路 `app_backend._search_knowledge_base`（AgentLoop / 网页 / 评测都走它）；MCP 工具是独立链路，本次不动。
- **依赖**：不新增重型依赖——重排复用已装的 `sentence-transformers.CrossEncoder`，只加 `jieba` + `rank-bm25` 两个纯 Python 小包。
- **原定步骤与验收标准（逐条对照实施结果）**：

  | # | 计划步骤 | 验收标准 | 结果 |
  |---|---|---|---|
  | 1 | 加依赖 `jieba` / `rank-bm25` | 冒烟：`Bm25Retriever().search("报名截止", 5)` 命中 Q3 目标文档 | ✅ 命中"学院初赛 6月24日"块 |
  | 2 | 新建 `src/hybrid_retriever.py` 三件套（惰性 + 单例） | 检索级：hybrid 走真实链路（不调 LLM），Q3 上下文含 `6月24日` + `6月10日` | ✅ 来源 16 条，格式兼容 `_parse_sources` |
  | 3 | 改 `_search_knowledge_base`，插入融合 + 可选重排 | 端到端：三档各跑 6 题对比 | ✅ hybrid 档 60/60 |
  | 4 | 三档消融（`vector` / `hybrid` / `hybrid_rerank`） | 回归：hybrid 档不劣于纯向量，前端来源解析不破 | ✅ 详见第 10 条 |

- **计划外的两处变动**（如实记录，论文可用：计划受挫 → 换方案）：
  1. **重排模型换人**：原计划 `mmarco-mMiniLMv2-L6-H384`（~100MB），hf-mirror 镜像 **404** 不可用；改为 `BAAI/bge-reranker-base`（~440MB，中文精排标准）。代价是模型体积与首次加载时间，换来"下得下来"。
  2. **`RERANK_TOP_N` 8 → 16**：消融发现 N=8 会把宽泛题埋在补块里的关键句截掉，N=16 则只优化排序、不牺牲召回。计划里写的是 8。
- **改造当时的库快照**：**6432 块 / 1121 篇**——这是**重建 bug 修复前**的数字（见第 11 条），修复后为 5919 块 / 1194 篇。引用时别把这两个数混用。
- **原计划里列为"后续可选"的两项，后来都做了**：MCP 工具同步混合检索（`search_knowledge_base` 复用主链路）、README 更新检索链路说明。

### 7. 新增依赖
- `jieba 0.42.1`（中文分词）、`rank_bm25 0.2.2`（OKAPI BM25 打分）。轻量纯 Python 包。
- 重排用已装的 `sentence-transformers` 的 `CrossEncoder`，不新增重型依赖。

### 8. 新增 `src/hybrid_retriever.py`（检索三件套，惰性 + 单例缓存）
- `Bm25Retriever`：懒加载全量块（6432 块）jieba 分词建倒排索引；`search(query, top_n, year)` 全库打分 → 取 top30 → 按年过滤 → 截断；distance 由归一化 BM25 分换算，保持"相似度%"展示格式一致。
- `rrf_fuse(vector_results, bm25_results, k=60, top_n)`：Reciprocal Rank Fusion 名次融合，无权重参数、稳健；按 text 去重，重复块保留更高相似度。
- `Reranker`：`BAAI/bge-reranker-base`（中文精排标准，~440MB），仅开关开启才加载；`rerank(query, candidates, top_n)` 对 (query, 文本) 对精排。原计划 mmarco 小模型镜像 404，改为 bge-reranker-base；重排失败时原样返回全部候选（不截断，等价于关掉重排）。

### 9. 主链路接入混合检索（`_search_knowledge_base`）
新流程：库外闸门 → 年份过滤 → 向量+BM25 双路召回 → RRF 融合 top_k → 去重 → 同文档补块 → 可选重排 → 格式化（格式不变，兼容前端 `_parse_sources`）。

新增 `.env` 开关：`RETRIEVAL_MODE=hybrid|vector`、`RETRIEVAL_RERANK=on|off`、`RERANK_TOP_N=16`
（写这条时最初是 8，当天消融发现 N=8 会截掉宽泛题的关键句，随即改为 16——见上面「计划外的两处变动」与第 10 条。代码与 `.env.example` 现均为 16）。
鲁棒性：jieba/rank_bm25 缺失或 BM25 建索引失败 → 自动回退纯向量，不崩。

### 10. 混合检索消融实验
- 同一 6 题，三档：`vector` / `hybrid` / `hybrid_rerank`（脚本 `eval_hybrid.py` 已随清理删除）。
- 每档每题记录**检索级关键句命中**（与 Qwen 评分解耦，只验证检索器功能）：
  - Q3：`报名截止` `6月24日` `6月10日`
  - Q5：`3月3日` `3月15日` `3月20日` `台账`

### 消融结果（2026-08-08）
关键句命中：Q3 总 3 句（报名截止/6月24日/6月10日）、Q5 总 4 句（3月3日/3月15日/3月20日/台账）。

| 模式 | Q3 检索级 | Q5 检索级 | 说明 |
|---|---|---|---|
| vector（基线） | 2/3 | 4/4 | 缺"报名截止"字面（片段截断 800 字） |
| hybrid | 3/3 | 4/4 | 两路融合，Q3 补上字面命中 |
| hybrid_rerank（N=8） | 3/3 | 0/4 | 重排截断到 8 条，挤掉补块里的关键句（模型首跑 mmarco 镜像 404 → 换 bge-reranker-base） |
| hybrid_rerank（N=16） | 3/3 | 4/4 | 重排只排序不牺牲召回，推荐配置 |

**BM25 独立价值（探测证据）**：对 8 条关键词查询，BM25 均引入了纯向量 top8 漏掉的来源，例：
- 「转专业」→ 向量漏、BM25 引入《智能工程学院2025级普通本科生转专业工作实施细则》
- 「寒假」→ BM25 引入《关于做好2026年寒假假期学生教育管理工作的通知》

**结论**：
1. 对本基准 6 题，关键句命中已被同文档补块覆盖，三档（vector/hybrid/rerank-N16）Q3/Q5 检索级命中均接近饱和；hybrid 补上了 vector 在 Q3 缺的"报名截止"字面。
2. 混合检索的增量价值在**向量初始召回漏掉的文档**上（关键词精确命中、语义重叠低时更鲁棒）——论文应强调的定位。
3. 重排 N=8 截断会伤宽泛题召回，N=16 恢复——默认 RERANK_TOP_N 已设为 16。

## 2026-08-08 ｜ 批次 3：全量库分块消融 + 三个数据 bug 修复

### 11. rebuild 覆盖 bug（块 ID 撞车）与 source 撞车
- **改了什么**：`rebuild_kb.py` 块 ID 从 `sha256(标题)` 改为 `sha256(相对文件路径)`；source 标签从「文件名 stem」改为「相对路径（分类/文件名）」。
- **为什么**：跨分类同名文档（65 组 / 141 篇）标题相同 → 块 ID 撞车被 Chroma 后写覆盖，整篇文档丢失（块数 6432→5507 的元凶）；source 用 stem 则补块时同名文档被当成一篇。
- **效果**：全量 1194 篇全部入库（300/50 重建 5919 块）；Q3 检索遗漏（历史 0 分）彻底修复——全档 Q3 关键句 3/3 命中。

### 12. chroma_db 损坏定位与修复
- **现象**：500-70 档 eval segfault 后，所有 rebuild 都在 `chromadb.api.rust._count()` 崩（Windows access violation），日志在模型加载后中断。
- **排查**：`python -X faulthandler` 定位到 `_count()`；全新临时库 count 正常、现有库 count 崩 → 现有库 sqlite/HNSW 索引损坏。
- **修复**：删除 chroma_db 重建（源头 scraped_docs 完好，库为可再生派生数据）。
- **教训**：`| tail` 会掩盖 segfault 退出码（假 exit=0），排查崩溃须直接取 python 退出码或用 faulthandler。

### 13. 嵌入模型离线加载
- **改了什么**：消融脚本加 `HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1`。
- **为什么**：sentence-transformers 每次加载模型都发 hf-mirror.com HTTP 校验，网络异常时加载挂起/segfault。
- **效果**：模型加载 <3 秒，离线稳定。

### 14. 全量库分块参数消融（三阶段，1195 篇全量，修复版重建）
| 阶段 | 范围 | 方法 | 结论 |
|---|---|---|---|
| 1 粗网格 | 12 组合（块 200-500 × 重叠 30-70） | 检索级关键句命中 | Q3 全档 3/3；Q5 台账由重叠主导（50/70 命中、30 缺）；probe 5/6 平 |
| 2 细网格 | 7 组合（300-50 → 500-60） | 完整 6 题链路 + 关键句 | 答案质量全档满分，分块参数不再是瓶颈 |
| 3 top_k | 5/8/12/16 | 完整 6 题链路 | 8 最优，5 有损（Q2 丢 4/17），12/16 无增益 |

**打分验收（DeepSeek + 同一评分规则，60 分制）**：300-50 首次 54/60（Q4 4 分：LLM 偶发把 2025 年三下乡安排当答案，个人申报 6月30日 应为 2026 年 7月10日）→ 重跑 **60/60**；300-70、350-60 均 **60/60**。

**最终参数：CHUNK_SIZE=300 / OVERLAP=50 / TOP_K=8**（保持默认，与 10 文档消融一致，全量验证满分）。

**已知隐患（不排期）**：Q4「最近有安排暑期社会实践」query 隐含年份倾向，检索器不敏感，2025 年通知常排在 2026 年前（300/50 稳定如此），LLM 偶发用错年份。
**2026-09-17 评估后决定不做**，理由三条：①显式年份已可用（`_extract_year` + Chroma `where={"year": year}` 的 ±1 年窗口），缺的只是隐性时效词（「最近」「今年」）；②失败形态是"偶发用错年份"的质量瑕疵，不是 Q6 那种归属错误，而它要改**检索排序**，得重跑消融、可能拖累基准；③文档原先写的方案「加权/过滤最新年份」本身不成熟——「去年的心理健康工作」就该往旧了查，无脑提权最新年是错的。真要做，得先做时间词识别（最近/今年/最新 ↔ 去年/往届），那是**新功能**不是修 bug。

### 15. 召回自检 —— 图式状态机 + 低置信度拒答（2026-09-17）

- **改了什么**：
  - 新增 `src/recall_guard.py`：图式状态机，四节点 `retrieve → grade → format|refuse`，条件边 + **改写重检环**。
  - `_search_knowledge_base` 拆成 `_retrieve_candidates`（返回**信封** `{candidates, short_circuit, timings}`）+ `_format_context` + `_search_plain`，公开同步 API 不变。
  - `rrf_fuse` 融合时**另存** `vector_distance`（保留向量路原始余弦距离）。
  - `_call_llm` 加 `system/tools/max_tokens/temperature` 覆盖口（默认值全保持原状，主循环零变化）。
  - `_get_vector_store` 补双检锁（原先无锁，FastAPI 与 MCP 同进程两条线程并发首访会双建）。
  - 开关 `RECALL_GUARD`（当时**默认 off**，保持改造前行为）+ `RECALL_GUARD_MAX_ATTEMPTS`（默认 1 = 环关）。
  - ⚠️ **2026-10-16 补记：`RECALL_GUARD` 默认值已由 `off` 翻为 `on`。** 当时留 `off` 的理由是
    "当消融基线、保持改造前行为"，**不是**效果判断——而下面这张消融表的证据全在反方向
    （负例 0/6 → 6/6、无关题 0/4 → 4/4、正例零误拒，代价仅负例 +0.8s）。论文里写的是它**开着**的

    在 `.env` 显式写明。跑 `off` 对照仍可：`RECALL_GUARD=off python eval_baseline.py`
    （`load_dotenv` 不覆盖已存在的环境变量，显式传入必胜）。**连带**：`eval_baseline.py` 未显式设

- **为什么**：**低置信度拒答**是真功能缺口。改造前 `distance_threshold=0.85` 赋值后**从未被读过**（`vector_store.py` 的 `search_similar` 不引用它）；唯一能拒答的 `_refuse_out_of_kb_school` 只做**校名**校验，问「河南工学院食堂几点开门」这种**本校但库里没有**的题，会把最不相关的块塞给 LLM 让它编。补这个缺口需要条件分支 + 环，这正是状态机相对 if/else 的价值所在。
- **阈值必须从真实库标定**（`my_rag_collection` 实测向量余弦距离）：

  | query | 最佳距离 |
  |---|---|
  | Q5 心理健康 / Q3 报名截止 / Q4 暑期实践 / Q1 端午 / Q2 运动会 | 0.143 / 0.203 / 0.249 / 0.255 / 0.307 |
  | 转专业（BM25 独立价值案例） | 0.384 |
  | 河南工学院食堂几点开门 | 0.465 |

  动态范围只有 0.14~0.61 —— 那个 `0.85` **永远不可能触发**。故取 `PASS_DIST=0.30`（基线 5 题全部 ≤0.307 → 基本免检）。**换 embedding 模型后必须重新标定**。
- **两个关键实现决定**：
  1. **没有一个跨检索来源统一的相似度分数可以卡阈值**。融合后 `distance` 可能是 BM25 的归一化分（第一名恒为 0.0 → 显示"相似度 100%"），也可能是补块继承来的。唯一可信的是向量路原始余弦距离，由 `rrf_fuse` 单独留在 `vector_distance` 字段。**"筛 origin=='vector' 再取距离"会拿到空集**——RRF 保留 distance 更小的那份，而 BM25 第一名恒为 0.0，几乎总赢。
  2. **只有「快通过」没有「快拒答」**：距离低 ≠ 答案在库里（`转专业` 距离 0.384 看着相关，正确文档却不在向量 top8）。所以快筛**只能证伪、不能证真**——单边放行安全，单边拒答会误杀这类靠 BM25 捞回来的题。
- **效果**（`eval_guard_probe.py`，真实检索链路，硬负例 6 + 无关题 4 + 正例 5）：

  | 配置 | 硬负例拒答 | 无关题拒答 | 正例放行 | 耗时（负例/正例） |
  |---|---|---|---|---|
  | `RECALL_GUARD=off`（= 改造前） | **0/6** | 0/4 | 5/5 | 0.26s / 0.27s |
  | `RECALL_GUARD=on` | **6/6** | 4/4 | 5/5 | 1.04s / 0.45s |

  改造前 6 条硬负例全部放行，每条往 LLM 上下文里塞 6.2k~8.8k 字符的无关内容；开启后全部拒答，正例**零误拒**，且正例耗时只涨约 0.2s（距离够近走快通过通道，不调判官）。
- **消融：环不开**（`RECALL_GUARD_MAX_ATTEMPTS` 1 vs 2）。干净负例上环开环关**打平**（都 6/6、4/4），环**没带来任何收益**；但在灰区题「招生办咨询电话」上环有害——环关正确拒答，环开翻成放行（**两次独立运行复现**）。机理：判官第二轮**不记得自己已经判过不充分**，改写重检后对着同样无关的新片段重新判、翻成 sufficient，**把一次正确的拒答变成了放行**。无收益 + 有反效果 → 默认关环，代码保留可开关（消融要能复跑）。
- **已知边界**：判官判的是**相关性**而不是**可答性**，所以「主题词在库、具体事实不在库」的灰区题（如「现任校长是谁」，库里只有外单位领导的人名）会被放行。这不是阈值能修的——要么改判官提问方式（问"片段能否支撑回答"而非"是否相关"），要么走 tool_use 结构化输出。另一条路是让判官带上「上一轮已判不充分」的上下文后重开环。
- **⚠️ 顺带发现：6 题基准的 60/60 有 ±10 分采样噪声。** 为验证「重构是否改变行为」用 **HEAD 原码**跑了两遍：**60/60 与 50/60**（同一份代码！）。我改后的 guard=off 两遍则是 50/60、57/60。根因是 Q6 这类题要过**两级 LLM**（回答 + 打分）：某次 LLM 把工具参数写成 `query='招生录取分数'`——**丢了校名**，库外闸门没东西可拦，于是返回 20 块河南工学院分数，回答里如实列了 **52 个**三位数字，评分 LLM 按「含基准表外数字即判幻觉」给了 0。检索层两次完全一致，差别只在**模型最后那段回答要不要多嘴抄数字**。**结论：60/60 是单次采样、不是稳定性质；自检层的效果必须用检索层的确定性指标量（本条目这张表），不能用 60/60 量。**

### 16. 首句净化 —— 扣住工具调用前的英文旁白（2026-09-17）

- **改了什么**：
  - 新增 `src/stream_gate.py`：`OpeningGate`，每轮扣住流开头，直到出现**第一个汉字**。
  - `app_backend.run_stream` 的流式排空循环接上闸门：`gate.feed(delta)` 决定下发什么，轮末 `gate.finish(had_tool_use=...)` 收尾。
  - `SYSTEM_PROMPT` 加第 16 条：调用工具前不输出任何文字说明、全流程只用中文。
- **为什么**：回答的第一句是英文旁白——

  > `I'll search the knowledge base for information about the 2026 Dragon Boat Festival holiday根据知识库中的通知，河南工学院…`

  模型在发起工具调用前先吐一句英文说明，而 SSE 是**逐 delta 直发**的，等这一轮结束、看到 `tool_use` 时英文早已显示在用户屏幕上。**这一轮的文本从头到尾都不属于回答**：`run_stream` 往 `messages` 里只 append 了 tool_use 块，**文本块被丢弃**——它本来就没被当成答案，却被实时播了出去。
- **是既有缺陷，不是改造引入的**：用 HEAD 原码复跑确认，6 题基准里 **4~5 题**首句都是这个旁白。

  | | prerf(HEAD) | prerf2(HEAD) | 本次改造 guard=off | 本次改造 guard=on |
  |---|---|---|---|---|
  | 出现题数 | 4/6 | 4/6 | 5/6 | 3/6 |

- **为什么用「汉字」当放行信号**：`tool_use` 块在流里**排在文本块之后**才到达，等它到就已经太晚了；而本轮是纯文本轮还是工具轮，要等整轮流完才知道。**「汉字」是唯一在流开头就能拿到、且能区分旁白与正文的信号**（SYSTEM_PROMPT 规则 9 要求用中文回复，正文必然含汉字）。
- **行为**：
  - 出现汉字 → 扣住的英文前缀丢弃，从汉字起原样放行。正文以汉字开头 → **流式几乎无延迟**（第一个 token 就出字）。
  - 整轮无汉字 + 有 `tool_use` → 扣住的就是旁白，丢弃。
  - 整轮无汉字 + 无 `tool_use` → 是一段正常的纯英文/数字回答，**整段补发**（不能把英文提问的回答吃掉）。
- **测试**：`tests/test_stream_gate.py` 10 条（纯字符串，零依赖），含「逐字喂与整段喂结果一致」（切片边界不影响结果）。全套 **106 passed**。
- **已知边界**：闸门只认「汉字」，英文旁白后若**同轮**又跟着中文旁白（如 `I'll search… 让我查一下知识库。`）再调工具，那段中文旁白会在开闸瞬间放行、漏到前端。实测判官的旁白都是纯英文，未遇到此情况；真要根治得让模型（规则 16）或改为延迟整轮下发。

### 17. 库外主体闸门二次校验 —— 堵住「LLM 改写掉校名」的绕过路径（2026-09-17）

- **改了什么**：
  - 新增 `_guard_tool_call(name, user_question)`：工具调用前用**用户原话**再过一次库外主体校验，命中就不跑检索。
  - `AgentLoop.run_stream` 与 `AgentLoop.run` 两处工具调用点都接上（MCP 路径不传原话，行为不变）。

- **不会误伤**：`_refuse_out_of_kb_school` 只要在 query 里看到主体校名就早退放行，所以比较类问句「河南工学院和河北工学院哪个好」照常放行（已测）。只对 `search_knowledge_base` 生效，时间/计算/天气不受影响。
- **测试**：`tests/test_out_of_kb_guard.py`（8 条，纯字符串，钉住两层闸门的分工）+ `tests/test_q6_rewrite_integration.py`（4 条，**假 LLM 端到端**复现「LLM 把 query 改写成 `招生录取分数`」这条路径，验证闸门真的接在 `run_stream` 上而不是死代码）。全套 **118 passed**。

  - **新增 `.env` 配置 5 项**：`SCRAPE_SCHEDULE_ENABLED` / `_HOUR` / `_MINUTE` / `_PAGES` / `SCRAPE_CATCHUP_DAYS`。
  - **顺带清理**：`app_fastapi.py` 删掉已无用的 `from fastapi import BackgroundTasks`（改用 `create_task` 后唯一使用点消失）。
- **为什么这么做**：
  1. **爬虫本来就是增量的，定时只是加个触发器**——`campus_scraper/storage.py` 的 `is_scraped(url)` 按 URL 去重、`DATE_FILTER_DAYS=730` 限窗口、`pipeline` 逐分类落盘入库，重复跑不会重复入库，只捞新增文章。**但绝不能让定时任务去重建库**：`rebuild_kb.py` 是清库重灌（`clear_all` + `rebuild_` 前缀 id），与爬虫的 `scrape_` 前缀是两条链，混跑会互相覆盖。
  2. **不引调度框架，手写 asyncio 循环**：与第 20 条「撤掉编排框架」的取向一致，也省一个依赖。每轮重算目标时刻，机器休眠或系统时钟调整造成的偏差会自然纠正，不会越跑越飘。
  3. **启动补跑是必需品，不是锦上添花**：服务不常驻时，凌晨窗口大概率在关机状态，「每天 3 点」等于永不触发。判据直接取 SQLite 里已有的 `last_scraped_at`，不新增存储。
  4. **定时与手动必须共用同一道闸**：见下「踩过的坑」第一条。
- **一并归档的「踩过的坑」**：
  - **`_scrape_running` 是进程内变量，跨进程不共享**：若把定时器放到另一个进程（如 Windows 任务计划程序跑独立脚本），它和 FastAPI 进程各持一份标记，凌晨定时跑起来的同时有人点一下 `/scrape/start`，就是**两个爬虫同时打学校官网**——原本防重复触发的那道闸直接失效。故调度放在**服务进程内**，与手动触发共享 `_spawn_scrape`。将来若真要外部调度，必须改成文件锁，或让外部只调 HTTP 接口。
  - **后台任务必须留一份引用**：`asyncio` 只对 task 持**弱引用**，不存的话任务可能在爬取途中被 GC 掉、静默中止。故新增模块级 `_scrape_task`。（原实现用 `BackgroundTasks.add_task`，由 Starlette 持有引用，不存在这个问题。）
  - **重启会打断补跑并让它重来**：补跑判据是「上次**成功**爬取」的时间戳——爬取中途重启既不更新该时间戳、也不记「已跑过」，下次启动会重新补跑。日常够用（爬起来就完了）；开发期频繁重启会让爬虫反复起跑，调试时把 `SCRAPE_CATCHUP_DAYS=0` 关掉即可。

### 25. 修复 TLS 握手失败：全站爬不动（2026-10-11）

- **现象**：`/scrape/start` 触发后 13 个分类**全部**请求失败，`scraper_cache.db` 一条记录都没增加；日志里刷的是 `Cannot connect to host www.hait.edu.cn:443 ssl:default [[SSL: SSLV3_ALERT_HANDSHAKE_FAILURE] sslv3 alert handshake failure]`。但同一 URL 用 `curl` 打开是 `HTTP 200`。
- **改了什么**（`campus_scraper/scraper.py`）：
  - 新增模块级 `_SSL_CONTEXT = ssl.create_default_context()` + `set_ciphers("DEFAULT@SECLEVEL=1")`；
  - `fetch_page()` 的 `session.get(...)` 挂上 `ssl=_SSL_CONTEXT`。
  - 因为**所有爬虫路径都汇聚到 `fetch_page` 这一个函数**（`scrape_category` / `scrape_article` / `crawl_ablation.py` 全走它），所以一处改动覆盖全站。
- **根因**：hait.edu.cn 全站只提供 SHA-1 密码套件（实测协商结果为 `AES128-SHA`），而 **Python 自带的 OpenSSL 3.0 默认安全级别是 `SECLEVEL=2`，会直接拒绝 SHA-1**，于是在握手阶段就被拒。**证书本身完全正常**（`*.hait.edu.cn`，河南工学院，2027-03 到期），所以只放宽密码套件等级、**证书校验保持开启**。
- **为什么 2026-08 那次全量爬取还能通**：不是我们这边变了——是**对方服务器后来改了 TLS 配置**。同一份代码、同一台机器，两个月前能爬、现在不能爬。
- **一并归档的「踩过的坑」**：
  - **`curl` 能打开 ≠ 爬虫能爬**。两者用的是**不同的 TLS 栈与安全级配置**：curl（Git Bash 自带）默认接受老密码套件，Python 的 OpenSSL 3.0 不接受。所以「我用浏览器/curl 明明能访问」**不能**作为"站点可达"的判据——排查这类问题必须用**爬虫自己的 HTTP 客户端**复现。
  - **报错信息指向的是握手，不是网络**。`Cannot connect to host` 这半句容易让人去查 DNS / 防火墙 / 代理，真正有信息量的是后半句 `SSLV3_ALERT_HANDSHAKE_FAILURE`——它明确说**连接建立了、是 TLS 协商被对端拒绝**。看异常要读到最后一个冒号之后。

- **为什么这么改**：**页数原本是每天固定付出的成本，而其中绝大部分是纯等待。**
  1. **实测数据**（2026-10-11）：列表页一页约 18 篇、覆盖约 6 个月；跨页**严格新→旧且无缝衔接**——通知公告第 1/2/3 页分别是 `10-10~09-23` / `09-22~09-03` / `09-02~08-05`，学校新闻第 1/2/3 页 `10-10~09-18` / `09-18~09-05` / `09-05~08-23`。所以本页一旦有已爬内容，后面的页只会更旧、必然也已在缓存里。
  2. **代价错配**：改动前每页之间无条件休息 3~8 分钟，13 分类 × 2 页的**日常空跑要 1.3~2 小时，其中约 72 分钟是纯 sleep**，而真实工作量只有 26 个列表页请求（约 3 分钟）。改动后日常跑完第 1 页即停，约 3~5 分钟。
  3. **`max_pages` 的语义从「固定成本」变成「上限」**：有紧急积压时才会往后翻，所以敢给补跑配一个更大的值，而平时不必为它付费。
  4. **日常与补跑需求相反，不该共用一个值**：日常只要追顶部新增（1 页足够），补跑要追赶数月的积压（需要更深）。旧配置两者共用一个数，等于"日常嫌多、补跑嫌少"。
- **一并归档的「踩过的坑」**：
  - **页首可能有置顶项，列表页并非严格有序**：通知公告第 1 页头部是 `2026-03-20`（置顶旧文），其后才严格递减（`10-10 → 09-23`）。所以**不能**用"第一条比第二条新"之类的简单有序性假设；本判据对置顶项免疫——置顶的是旧文章，命中缓存只会让停止来得更早，不会漏抓。
  - **早停的风险是静默漏抓，方向不对称**：慢只是慢，漏是内容永久缺失且**没有任何报错**。所以 5 条测试里有 2 条专门守反方向（连续两页全新时必须翻满、`max_pages` 是上限），并用"临时禁用判据 → 3 条失败 / 恢复 → 5 条全过"验证过测试非空转。

### 27. 修复「正文被包在 `<form>` 里」导致整篇文章静默丢失（2026-10-11）

- **现象**：电缆工程学院通知的列表页明明有 5 条未爬 URL（含一条 `2026-10-10`），但这一轮爬取该分类**一条标记都没写**，日志里只有一句 info 级的"跳过（无正文内容）"。
- **根因**：动易的这个模板把**整篇正文**包在 `<form>` 里——`<div class="page_content">` 共 890 字，实测**100% 落在其中的 `<form>` 内**。而 `_REMOVE_TAGS` 无条件删 `<form>`，`_clean_element()` 一个 `decompose()` 下去，890 字变 0 字。
- **为什么这个 bug 特别阴**：
  1. **它不报错**。"正文为空"是 `scrape_article()` 的正常业务分支（确实存在纯图片页），所以日志级别只是 info，看不出异常。
  2. **失败的文章不留痕迹**。返回 `None` 就不写 `mark_scraped`，缓存库里查不到"它来过"——从缓存库看，这个分类和"从没被访问过"长得**一模一样**。
  3. **它会每轮复发**。URL 没被标记 → 下一轮再抓一次 → 再失败一次。所以不是"丢一次"，是"永远丢，且每轮白付一次请求成本"。
  4. 这个坑是**在核对"库内纹丝不动是不是卡死"时顺带查出来的**（改进记录第 26 条那一轮），不是被任何报错或监控发现的。换句话说：**当前没有任何机制能发现它**。
- **改了什么**（`campus_scraper/html_parser.py`）：`_should_remove()` 里给 `<form>` 开例外——文字量 ≥ `_CONTENT_FORM_MIN_CHARS`（200 字）的 form 当正文留着，不当控件删。
- **为什么用文字量而不是 class/id 关键词**：真正该删的查询/登录表单只有几个字，正文动辄几百字；而搜索容器本身另有 `_REMOVE_KEYWORDS` 里的 `"search"` 兜着（实测 `<table class="searchstyle1092668">` 就是被关键词规则删掉的，不依赖 form 那条规则）。
- **验证**：3 条原先全废的 URL 现在分别抽出 **895 / 395 / 1394 字**；原本就通的对照页 **735 字不变**（无回归）。新增 `tests/test_html_parser_form_content.py`（5 条），并按「临时退回旧行为 → 2 条失败 / 恢复 → 5 条全过」验证过测试非空转。全套 **106 → 111 passed**。
- **顺带澄清影响范围**：同批"0 产出"的分类里，`马克思主义学院通知` 第 1 页 10 条**全在缓存**（0 产出是正常的，不是 bug），`学生处通知` / `团委通知` 的未爬文章解析都正常。所以这个坑集中在 dlxy 那个模板上，**不是全站性的**。
- **历史数据无需修补**：失败的文章从未被标记，所以下一轮爬取会自动重试并（这次）成功入库——不存在"已经丢了要靠手工回补"的数据。

### 28. 修复「已爬标记早于入库」导致中途停机永久丢文章（2026-10-11）

- **现象**：两次中途停机（17:15:42、19:48:22）之后核对知识库，发现 **20 篇文章在缓存库里标着「已爬」，正文却根本不在 ChromaDB 里**：14 篇学校新闻（17:14:03–17:15:42 标记）+ 6 篇马克思主义学院新闻（19:47:52–19:48:22 标记）。两批都恰好是**停机时所在分类的收尾那几篇**。
- **怎么查出来的**（不是猜）：增量入库的块 id 形如 `scrape_{发布日期}_{content_hash[:8]}_{序号}`，中间那段就是该篇的 `content_hash` 前缀，于是**「哈希在不在库内 id 里」=「这篇文章在不在库里」**。当天标记 137 篇、库内只找到 117 篇的哈希，**差额 20 篇**；反向验证：在库的那篇命中 10 个块（`scrape_2026-09-30_daf38552_0..9`），丢的那篇命中 0 个。
- **根因**：`mark_scraped()` 是**逐篇**写的（在 `scrape_category()` 里），而入库（落盘 .txt → 分块 → 嵌入）是**整个分类爬完才做**（`pipeline.run_scrape_pipeline()`）。于是「标记了但没入库」的窗口**横跨整个分类**（实测一个分类 0.5~17 分钟）。进程在这个窗口里被杀 → 标记留在库里、正文只在内存里 → 正文永久消失。
- **为什么这个 bug 特别阴**：
  1. **不报错**。被杀的进程不抛任何异常，只是不再写日志，"跳过（无正文内容）"之类的话都没有。
  2. **之后每轮都被静默跳过**。`is_scraped()` 看到标记就跳过，所以不是"丢一次"，是**永远丢**。
  3. **标记反而成了"这段内容在库里"的假证据**。`CLAUDE.md` 那条 `unaccounted_chunks == 0` 恒等式**完全查不出来**——它数的是库内块的来源归属，看不到"标记了却不在库内"的缺口。也就是说，这是监控体系的**盲区**。
  4. **触发它的正是正常运维**：不需要崩溃、断电，**手动停一次服务**就够了。
- **改了什么**：
  - `campus_scraper/scraper.py`：爬取阶段**不再落标记**，只把文章交回去；另加一张 `seen_urls` 兜住"同一轮内重复出现的 URL"（原本靠 DB 标记去重，标记挪走后会失效；它**不计入**早停判据 `seen_before`）。
  - `campus_scraper/pipeline.py`：`_split_and_embed()` 在**每篇 `save_documents()` 成功之后**落标记，并支持 `mark_fn` 注入（测试用）。`dry_run` 分支仍照旧直接标记——它只收 URL、从不入库，不存在标记与内容脱节。
- **为什么这么改**：原代码的注释里就写着"每爬完一个分类马上落盘入库……任何时刻中断，已爬内容都已安全入库，不会被『已标记未入库』丢失"——**代码没有兑现它自己声明的意图**。改完后不变量变成逐篇的「**标记 ⇒ 已入库**」。代价只是：万一在单篇入库时挂掉，下一篇重爬一遍。**白干一遍 vs 永久丢内容**——方向不对称时就该选前者。
- **验证**：
  - 新增 `tests/test_mark_after_embed.py`（4 条），钉的是**不变量本身**：① 标记必须晚于入库调用（把两者写进**同一条事件日志**，断言 `save, mark, save, mark…` 的**顺序**，而非各自条数）② 入库失败就不许标记 ③ 一篇切多块只标记一次 ④ **爬取阶段一律不许落标记**（防"搬回去"的回归）。
  - **变异验证**：把标记挪到 `save_documents()` **之前** → 3 条失败（第 4 条仍过，它守的是反方向）；恢复 → 4 条全过。
  - **真实组件集成验证**：真 `VectorStore` + 真 `mark_scraped`（均指向临时目录，不碰生产库）→ 入库 10 块、块 id 为 `scrape_2026-10-11_0dc49ad6_0`、两篇均落标记。
  - 全套 **111 → 115 passed**。
- **数据修补**：缓存库先备份为 `campus_scraper/scraper_cache.bak-20261011.db`（后缀写成 `.db` 是为了命中 `.gitignore` 的 `*.db`，免得几百 KB 的库备份被顺手提交），再撤掉那 20 条标记（1538 → 1518 条）。撤完后「当天标记 117 篇」与「库内当天实际入库 117 篇」**对上了账**。这 20 篇都在各自列表页第 1 页，所以下一轮哪怕只跑 1 页的日常增量也会自动补回——**不存在需要手工回补的数据**。

### 29. 相对时间词：检索层落地成日期区间（2026-10-17）

- **现象**（线上实测）：
  - 「昨天有没有新的通知」→ 拿 9 月 18 日的旧通知作答；
  - 「昨天有什么新的新闻吗」→ 回答「知识库没有新闻资讯」；
  - 「昨天有什么智能工程学院有新通知吗」→ 说「文档没有日期」，然后列了一串不相干的通知。
- **根因有三层，缺一层都修不好**：
  1. **检索层完全不看 `publish_date`**。向量按「通知」二字的语义捞旧文，BM25 把「昨天」当普通词（没有任何文档命中），日期元数据入库了却从未参与过滤。
  2. **列表页的日期根本没取到**。动易各子站模板差异大：有的把日期做成**同 URL 的独立 `<a>`**（被当成第二篇文章）、有的日期是 `<li>` 里的**裸文本**、有的把日期写在**链接文字前缀**里、有的用 `h5.article-date`。实测教务处通知 / 智能工程学院通知 / 车辆学院通知 **100% 空日期**，智能工程学院新闻 99%，学生处通知 11.5%。
  3. **prompt 里没有「今天」**。模型不知道当前日期，「昨天」只能自己猜（或先调 `get_current_time`，但它不一定调）。
- **改了什么**：
  - 新增 `src/time_range.py`：确定性解析今天/昨天/前天、本周/上周、本月/上月、今年/去年、`最近 N 天/周/月`、显式 `YYYY-MM-DD` / `YYYY年M月D日` / `YYYY年M月`，以及「最近/近来/最新」的兜底窗口（`RECENT_WINDOW_DAYS`，默认 30）。返回闭区间 + 原始命中词。
  - `html_parser.py`：列表页日期按「同 URL 合并」处理（日期链接不再算一篇）；新增 `_extract_date_from_row()` 扫 `li/tr` 里的日期标签、裸文本、相邻文本节点；标题前缀日期拆到 `date` 字段；详情页日期 class 列表补 `article-date`。详情页无日期时用**列表页日期**兜底（`scrape_article(fallback_date=...)`）。
  - 入库元数据新增 `date_int`（`YYYYMMDD` 整数）：Chroma 的 `$gte/$lte` **只认数字**，传日期字符串会直接 `ValueError`；且同一个 key 只能有一个操作符，区间必须写成 `{"$and": [...]}`。
  - `app_backend.py` 检索入口：先把相对时间解析成区间；**泛问「最近有什么通知/新闻」**（去掉时间词、机构名、泛问词后主题词 ≤2 字）不再走语义检索，直接按 `publish_date` 倒序列出该时段文章（每篇取首块），并按「通知/新闻」后缀和查询中的学院名过滤；带主题词的问题（如「最近有没有转专业的通知」）仍走混合检索 + 日期过滤。相对时间是**硬条件**，不做「查不到就放宽」回退——宁可如实说没有，也不拿旧文冒充。
  - `BM25Retriever.search()` 增加 `date_start/date_end`，在排序前先过滤候选，避免日期外的文档挤占 `top_n`。
  - `_call_llm` 自动在 system prompt 后追加当前日期/星期/时间；prompt 新增规则 17（相对时间要带具体日期检索、以片段「日期」为准）和 18（知识库确实含新闻，不要声称没有）。
- **历史数据修补**：新增 `backfill_dates.py`（只抓列表页建 URL→日期映射，不抓正文），回填 Chroma 的 `publish_date/year/date_int` 和 SQLite 缓存。必须等爬虫进程结束再跑（Chroma 单写者），跑完重启服务让进程内 BM25 重新建索引。
- **验证**（2026-10-17）：
  - 列表页 **1872 个 URL，100% 带日期**；Chroma **7200 块全部回填**（补出 `publish_date` 1450 块、`date_int` 7086 块），空日期块 **1913 → 114（1.6%）**。教务处通知 100% → 12.9%、智能工程学院新闻 99% → 7.8%，其余分类 0%。
  - 检索层确定性验证（不走 LLM）：`昨天有没有新的通知` → 2 篇 10-16 通知；`最近有什么新闻` → 8 篇 10-12~10-17 新闻按日期倒序；`上周有什么通知` → 全部落在 10-05~10-11；`上月有什么通知` → 全部 9 月；`昨天有什么智能工程学院有新通知吗` → 该学院通知最新只到 7-21（官网列表页实测如此），**如实短接「昨天没有相关内容」**。
  - 测试：新增 `tests/test_time_range.py`（7 条）；`tests/test_list_entry_regressions.py` 扩到 8 条（日期链接合并 / 裸文本日期 / 中文日期前缀 / 频道过滤 / **文章链接不能当分页**）；全套 **164 passed**。
- **顺带修掉**：材料学院首页没有分页，但「更多 >」箭头指向一篇文章，`extract_pagination` 把它当成了「下一页」。现在分页解析会跳过文章详情页链接（`info/{栏目}/{id}.htm`、`wbnewsid=`），否则真分页的站点可能被这条误判带偏、提前停爬。
- **遗留**：核对缓存库与 Chroma 时发现 **207 条 2026-08-07/08 首次全量爬取留下的「已爬但未入库」标记**（哈希在库内 id 里同样找不到），属第 28 条那个 bug 的修复前产物，且已超过当前增量爬取的翻页深度（早停会停在第 1 页）。要补回只能按 URL 逐篇重抓，暂未执行。（已于同日处理，见第 30 条。）

### 30. 补回 207 条孤儿标记，顺带修掉标题截断、死链入库、非法文件名（2026-10-17）

- **现象**：知识库里「已爬标记」和「实际内容」对不上账。按第 29 条的遗留核查，缓存库有 **207 条标记**对应的 URL 不在 Chroma，内容哈希也不在块 id 里。这批是 2026-08-07/08 首次全量爬取时、第 28 条 bug 修复前留下的孤儿——标记在、正文从未入库。
- **为什么必须手工补**：日常增量「遇到已爬 URL 即停」（早停判据），而这些 URL 早就在缓存里，第 1 页就会命中、直接停止翻页；`is_scraped()` 也会让它们永远被静默跳过。**不重抓就永久缺失**。而 `unaccounted_chunks == 0` 这个监控口径**查不出来**——它数的是库内块的来源归属，看不见「标记了却不在库内」的缺口（第 28 条已注明这是盲区）。
- **判据（两条同时满足才算真缺失）**：① URL 不在任何块的 `url` 元数据里；② `content_hash` 前 8 位不在任何块 id（`scrape_{日期}_{hash8}_{序号}`）里。只满足第 1 条的多半是同一篇内容换了 URL/日期入库，**不能重复补**。
- **改了什么**：
  - 新增 `recover_missing.py`：按上述判据出清单 → 逐篇 `scrape_article()` 重抓 → 校验哈希不在库 → `_save_clean_text()` + `_split_and_embed()` 入库（入库成功才落标记，沿用第 28 条的不变量）。支持 `--dry-run` / `--limit` / `--fix-titles`；**必须在服务与爬虫停止时跑**（Chroma 单写者）。
  - 发布时间超出 `DATE_FILTER_DAYS`（730 天）的文章不补——它们本来就不在知识库收录范围内。
- **顺带修掉三个会让补录静默失败的问题**：
  1. **标题被腰斩**：`parse_html` 按**第一个**连字符截站点后缀，把学年区间「2025-2026」拦腰砍断（「关于公布2025」）。改为 `_strip_site_suffix()`：只截**最后一个**分隔符之后、且尾部短（≤30 字）不含数字的部分。`--fix-titles` 对 26 个 URL 重抓重切，91 块；修完库内截断标题 **0 条**。
  2. **死链当文章入库**：动易对不存在的文章 ID 返回 **HTTP 200** + 一个「没有找到文章ID」的导航壳，正文能提取出几十个字，于是被当成正常文章切块——标题还成了「教务处（学位办、语委办）」。`scrape_article()` 现在识别固定文案直接返回 `None`；已入库的那 1 块垃圾已删除，缓存库标题改为 `（死链）…`，`find_missing` 据此跳过、不再反复重试。
  3. **Windows 非法文件名**：标题含 `"` 或 `|` 时 `write_text` 抛 `[Errno 22] Invalid argument`，而补录的 try 块把「落盘 + 入库」包在一起，**保存失败连嵌入也一起中断**（实测 4 篇：两篇「喜报」、一篇歌会、一篇「新工科」）。新增 `pipeline._safe_filename()` 统一替换 `<>:"/\|?*` 与控制字符、去首尾点和空格、限长 80；`recover_missing._doc_path()` 复用它，路径不再各写一套替换逻辑。
