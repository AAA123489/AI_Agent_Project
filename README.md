**1195 篇公开文档 / 13 个分类**变成可自然语言提问的知识库——答案**带出处**，
检索不到就**拒答**而不是编造。

## 为什么做这个

河南工学院官网的信息分散在 13 个栏目的上千篇通知里，学生要查「暑期社会实践什么时候截止」
「心理健康工作怎么安排」，得翻很久。而且**官网站内搜索是关键词匹配**——
问「报名截止时间」，搜不出埋在某篇通知中段的那句话。

于是做了这个系统：自然语言提问 → 自动检索相关文档片段 → 生成答案并**附上原文链接**。

**但真正让我花力气的是"拒答"。** LLM 在检索不到内容时会顺着上下文编：
问「河北工学院的录取分数线」，不管的话它会拿河南工学院的分数答你。
校园场景下这种错误是灾难性的——学生按错信息去报名。所以系统里有三道闸门专门防这个。

## 系统架构

### 离线：数据入库

```
河南工学院官网（13 个栏目）
   │  aiohttp 异步爬虫：限速 / 重试 / SQLite 去重（断点续爬）
   ▼
HTML → 纯文本（动易 CMS / JSP 模板适配，按栏目配选择器）
   │  sanitize_privacy 隐私脱敏（删手机号 / 邮箱，保留办公座机）
   ▼
递归切分器（300 字 / 50 字重叠）
   │  块 ID = sha256(相对路径)，source = "分类/文件名"
   ▼
paraphrase-multilingual-MiniLM-L12-v2 向量化
   ▼
ChromaDB（collection: my_rag_collection，5919 块）
```

### 在线：一次问答的全链路

```
用户提问
   │
   ├─[0] 查询缓存（Redis，命中则秒回，跳过下面全部）
   ▼
LLM（Agent 循环，工具调用，最多 6 轮）
   │  决定调用 search_knowledge_base(query=...)
   ▼
┌────────────── 检索层 _retrieve_candidates ──────────────┐
│ [1] 库外主体闸门  问外校 → 直接拒答，不进检索              │
│ [2] 年份过滤      query 含 20xx → Chroma where={year}    │
│ [3] 双路召回      向量 top-k  ∥  BM25 top-30             │
│ [4] RRF 融合      k=60 名次融合，另存 vector_distance     │
│ [5] 文本去重      同通知进两个目录 + 重叠窗口会产生重复块    │
│ [6] 罕见词精确召回 2/3-gram $contains 兜底（人名/专有名词） │
│ [7] 同文档补块     前3块 + 中段1块 + 末块，最多5篇，封顶20块 │
│ [8] 可选重排      bge-reranker-base，N=16（默认关）        │
└────────────────────────────────────────────────────────┘
   ▼
[9] 召回自检（LangGraph，可选）
   │   best_vector_distance ≤ 0.30 → 直接放行（不调判官）
   │   否则 → LLM 判官：sufficient / insufficient / off_topic
   │   不充分 → 拒答，不进 LLM 生成
   ▼
LLM 生成（SSE 逐 delta 下发，经「首句净化」闸门）
   ▼
回答 + 📎 参考来源（日期 · 文件名 · 原文链接）
```

```bash
cp .env.example .env
```

`.env` 里**必填**的只有 `API_KEY`；其余都有默认值，改配置不用改代码。

| 变量 | 默认 | 说明 |
|---|---|---|
| `API_KEY` | — | **必填**，DeepSeek API 密钥 |
| `API_URL` | DeepSeek Anthropic 兼容端点 | LLM 接口 |
| `MODEL_NAME` | `deepseek-v4-flash` | 模型 |
| `TEMPERATURE` | `0.3` | 消融最优（数字题对高温极敏感） |

| `QUERY_CACHE` | `on` | 查询级缓存开关 |
| `QUERY_CACHE_TTL` | `3600` | 缓存过期秒数 |
| `REDIS_URL` | `redis://localhost:6379` | Redis 地址（不装 Redis 也能跑，记忆/缓存静默降级） |
| `EXPERIMENT_TAG` | `baseline` | 对话日志分文件标签（消融实验用） |

## 关键设计

### 1. 混合检索：向量 + BM25 + RRF

**为什么加 BM25**：纯向量语义检索对「关键词精确命中」类信息鲁棒性不足。
典型例子——问「转专业」，**向量 top8 里没有**《转专业工作实施细则》：
语义上「转专业」和那份文件的通知腔重叠度不高，但 BM25 一眼命中。

| 组件 | 实现 |
|---|---|
| `Bm25Retriever` | jieba 分词建倒排索引；全库打分取 top30 → 按年过滤 → 截断 |
| `rrf_fuse` | Reciprocal Rank Fusion，`k=60`，**按名次融合而非分数** |
| `Reranker` | `bge-reranker-base`，**仅开关打开才加载**（省内存） |

**为什么用 RRF 而不是加权求和**：向量相似度（0~1 余弦）和 BM25 分（无上界）**量纲不可比**，
归一化后加权还得再调一个权重参数。RRF 只用名次，无参数、稳健。

> **一个非直觉的实现细节**：`rrf_fuse` 按 text 去重时会保留 `distance` 更小的那份，
> 而 **BM25 的第一名 distance 恒为 `0.0`**（`1.0 - score/best` 归一化的必然结果），
> 所以融合后的 `distance` 几乎总是 BM25 的归一化分，**不是余弦距离**。
> 后果：后来做召回自检要卡「向量距离阈值」时，「筛 `origin=='vector'` 再取 distance」
> **会拿到空集**。修法是让 `rrf_fuse` 融合时**另存 `vector_distance` 字段**——
> 这是全系统唯一可信的相似度信号。

**鲁棒性**：jieba / rank_bm25 缺失或建索引失败 → **自动回退纯向量**，不崩。

### 2. 四层检索增强

每一层都是**被一个具体败例逼出来的**：

| 增强 | 做法 | 解决什么 |
|---|---|---|
| **年份过滤** | query 含 20xx → `where={"year": ...}`，带 ±1 年窗口，空结果回退 | 跨年旧通知挤占检索名额 |
| **文本去重** | seen set | 同一通知被爬进两个分类目录 + 重叠窗口 → 内容相同的块重复占名额 |
| **罕见词精确召回** | 2/3-gram `$contains` 精确匹配 | 向量和 BM25 都漏掉的人名 / 专有名词（如获奖名单里的名字） |
| **同文档补块** | 按 `source` 拉该文档全部块补进来 | 宽泛问题的关键句埋在文档中后段，语义相似度捞不到 |

**罕见词兜底的三道防滥用护栏**（否则 `$contains` 会拖死检索）：

- `_EXACT_RECALL_MAX_MATCH = 20` —— 命中块数 ≤20 才当「罕见词」，高频词命中成百上千块就跳过
- `_EXACT_RECALL_MAX_INJECT = 3` —— 单次最多注入 3 块，防上下文膨胀
- `_EXACT_RECALL_MAX_SCAN = 10` —— 单次最多扫 10 次，限时防长查询拖慢

**同文档补块的顺序讲究**（每篇最多补 4 块、最多 5 篇、总封顶 `TOP_K+12=20`）：

- **前 3 块** —— 常规
- **中段 1 块** —— 关键句常埋在中间。这是 **Q5 的败因**修出来的：心理健康排查通知里
  「3月20日前台账钉钉」落在第 4 块，只补前 3 块会跳过它
- **末块** —— 落款 / 日期 / 联系电话在文末。这是 **Q10 的败因**修出来的

还有个细节：补块本身没跟 query 算过相似度，**沿用所属来源的最高相似度展示**，
不然列表里会出现「相似度 3%」的块，误导用户。

### 3. 召回自检（LangGraph 状态机）

#### 为什么做：一个真实的功能缺口

改造前系统里有个 `distance_threshold = 0.85` 配置——**赋值后从未被读过**
（`vector_store.py` 的 `search_similar` 根本不引用它）。它是个**死配置**，
给了「我做了阈值拒答」的错觉。

真正的拒答只有校名一道，而它**只做主体校校验**：query 含「河南工学院」就无条件放行，
**不做任何主题存在性校验**。结果——问 **「河南工学院食堂几点开门」**
这种**本校、但库里真没有**的题，系统会把最不相关的块塞给 LLM 让它编。

#### 图结构

```
START → retrieve → grade ─┬─(sufficient)──────────────────→ format → END
                          ├─(insufficient 且 attempt<max)──→ retrieve（环，attempt+1）
                          └─(off_topic 或 attempt>=max)────→ refuse → END
```

补这个缺口需要的正是**条件分支 + 环 + 显式终止条件**——这是状态机相对 `if/else` 的价值。
主对话循环仍是手写的 `AgentLoop`（未上框架）：那个循环太简单，上图是过度设计。

#### 阈值必须从真实库标定

用同一 embedding 模型实测库内原始向量余弦距离：

| query | 最佳距离 | 含义 |
|---|---|---|
| Q5 心理健康 / Q3 报名截止 / Q4 暑期实践 / Q1 端午 / Q2 运动会 | 0.143 / 0.203 / 0.249 / 0.255 / 0.307 | 基线题，库里确实有 |
| 转专业 | 0.384 | 灰区：靠 BM25 才捞得到正确文档 |
| **河南工学院食堂几点开门** | **0.465** | 目标硬负例：本校但库里没有 |
| 今天天气怎么样 / 推荐几部电影 | 0.603 / 0.613 | 真库外 |

**全射程只有 0.14 ~ 0.61** —— 那个 `0.85` **永远不可能触发**。故取 `PASS_DIST = 0.30`
（基线 5 题全部 ≤0.307 → 基本免检）。

> ⚠️ **换 embedding 模型后必须重新标定。**

#### 两个关键设计决定

**① 只有「快通过」，没有「快拒答」。**

距离低 ≠ 答案在库里。上面「转专业」距离 0.384 看着很相关，
但**正确文档不在向量 top8 里**。所以距离快筛**只能证伪、不能证真**：

- 距离 ≤ 0.30 → 判 sufficient（**证真安全**：这么近一定有料）
- 距离 ≥ 0.50 → **不单独拒答**，只要有任何非向量来源的候选就交给判官

**单边闸门**：单边放行安全，单边拒答会误杀「转专业」这类靠 BM25 救回来的题。

**② 判官输出走纯文本，不走 `tool_use`。**

DeepSeek 的 Anthropic 兼容端点对**具名 `tool_choice`** 支持不可靠。
判官输出单行：`VERDICT: sufficient|insufficient|off_topic | REWRITE: ... | EVIDENCE: <逐字抄自片段的一句>`，
只吃 query + top5 候选各 200 字，`max_tokens≈150`。

**双默认兜底**：解析失败 / HTTP 失败 / `text` 为空 → **一律 sufficient 放行**。
理由：宁可少拒答，不可误拒答，更不可**打断 SSE 流**。

> **一个坑**：路由函数必须做 verdict → 白名单归一化。LangGraph 1.2 内部
> `_branch.py` 是 `self.ends[r]`，返回 `path_map` 以外的 key 直接 `KeyError`。
> 而且 **`recursion_limit` 默认是 10007 不是 25**——靠它兜底等于没有兜底，
> 所以写了显式的 `attempt` 计数终止条件 + 专门的终止性测试。

#### 效果

探测集 = 硬负例 6 + 无关题 4 + 正例 5（`eval_guard_probe.py`，**真实检索链路**）：

| 配置 | 硬负例拒答 | 无关题拒答 | 正例放行 | 耗时（负例/正例） |
|---|---|---|---|---|
| `RECALL_GUARD=off`（= 改造前） | **0/6** | 0/4 | 5/5 | 0.26s / 0.27s |
| `RECALL_GUARD=on` | **6/6** | 4/4 | 5/5 | 1.04s / 0.45s |

改造前 6 条硬负例**全部放行**，每条往 LLM 上下文里塞 6.2k~8.8k 字符的无关内容。
开启后全部拒答，**正例零误拒**，正例耗时只涨约 0.2s（距离够近走快通过通道，不调判官）。

#### 消融结论：环默认关

`RECALL_GUARD_MAX_ATTEMPTS` 控制检索轮数：`1` = 不重检，`2` = 允许一次改写重检。

| | 硬负例 | 无关题 | 灰区题「招生办咨询电话」 |
|---|---|---|---|
| 环关（`attempts=1`） | 6/6 | 4/4 | 正确拒答 |
| 环开（`attempts=2`） | 6/6 | 4/4 | **翻成放行**（两次独立运行复现） |

- **干净负例上环开环关打平** → 环**没带来任何收益**
- **灰区题上环有害** → 机理：判官第二轮**不记得自己已经判过不充分**，
  改写重检后对着同样无关的新片段**重新判**，就翻成 sufficient，**把一次正确的拒答变成了放行**

无收益 + 有反效果 → **默认关环**，代码保留可开关（消融可复跑）。

#### 已知边界

判官判的是**相关性**而非**可答性**。所以「主题词在库、具体事实不在库」的灰区题
（如「现任校长是谁」，库里只有外单位领导的人名）会被放行。

### 4. 库外拦截（两层校验）

**问题**：问「河北工学院的录取分数线是多少」，库里当然没有，但放它进检索会捞回一堆
河南工学院的分数文档，LLM 顺势就把本校分数当答案答了（**张冠李戴的幻觉**）。

**做法**：正则识别 query 里的学校名（`XX大学 / XX工学院`），
凡**主体校（河南工学院）之外**的 → 直接拒答，不进检索。

**不误伤的三个细节**：

1. **泛指字过滤** —— `_is_internal_org` 维护校内机构名单，避免把「智能工程学院」
   （本校二级学院）当外校拒掉
2. **主体校早退** —— query 里出现「河南工学院」立刻放行，所以比较类问句
   「河南工学院和河北工学院哪个好」照常通过
3. **合作词例外** —— `_COLLAB`（牵头/联合/共同/与/和/邀/合作/主办/协办/参加/参赛/联）
   跟在外部校名后时放行，因为「河南工学院与XX大学联合举办」是本校的事

**第二层：用用户原话再校验一次。**

```
用户原话 ─┬─→ LLM 改写 ─→ 工具参数 → [闸门 A] → 检索
          └──────────────────────────→ [闸门 B] ─┘
```

**为什么需要第二层**：这道题要过**两级 LLM**（回答 + 打分）。实测**同一份代码**
跑两遍得到 60/60 与 50/60——根因是回答级 LLM 某次把工具参数写成 `query='招生录取分数'`，
**把校名改写掉了**。闸门 A 只看得到工具参数，于是没东西可拦。

闸门 B（`_guard_tool_call`）用**用户原话**再校验一次。
理由：**「问的是不是外校」是用户问题的性质，不是工具参数的性质**——
工具参数是 LLM 改写过的中间产物，随时可能把关键词洗掉；**用户原话里校名跑不掉**。
命中就不跑检索（省一次 Chroma + BM25）。

**拒答文案是强化的**：明确写「严禁补充河南工学院或其他学校的任何信息（含录取分数），
即使作为附加说明也不行，只拒绝不展开」。

### 5. 首句净化

**现象**：改造前回答的第一句是英文——

> `I'll search the knowledge base for information about the 2026 Dragon Boat Festival holiday根据知识库中的通知，河南工学院…`

**根因**（三条事实叠加，不是 Prompt 问题）：

1. 模型在发起工具调用前**先吐一句英文旁白**
2. SSE 是**逐 delta 直发**的，等这一轮结束看到 `tool_use` 时，英文**早已显示在用户屏幕上**
3. **这一轮的文本从头到尾都不属于回答**——`run_stream` 往 `messages` 里
   **只 append 了 tool_use 块，文本块被丢弃**

所以它本来就没被当成答案，却被实时播了出去。**用 HEAD 原码复跑确认这是既有缺陷**：
6 题基准里 **4~5 题**首句都是这个旁白。

**为什么用「汉字」当放行信号**：`tool_use` 块在流里**排在文本块之后**才到达，等它到就太晚了；
而本轮是纯文本轮还是工具轮，**要等整轮流完才知道**。
「汉字」是唯一**在流开头就能拿到、且能区分旁白与正文**的信号。

**行为**（`src/stream_gate.py` 的 `OpeningGate`）：

| 情况 | 处理 |
|---|---|
| 出现汉字 | 扣住的英文前缀丢弃，**从汉字起原样放行** → 流式几乎无延迟 |
| 整轮无汉字 + 有 `tool_use` | 扣住的就是旁白，**丢弃** |
| 整轮无汉字 + 无 `tool_use` | 是正常的纯英文/数字回答，**整段补发**（不能吃掉） |

**效果**：4~5/6 → **0/6**，答案其余部分完好，60/60 不变。

**已知边界**：闸门只认「汉字」，若英文旁白后**同轮**又跟着中文旁白
（`I'll search… 让我查一下知识库。`）再调工具，那段中文会被开闸瞬间放行。
实测未遇到过。

### 6. 分块与参数消融

**自研递归切分器**（`text_splitter.py`）：段落 → 句子（`。！？；`）→ 逗号 → 空格 → 硬切；
贪心累积到 `CHUNK_SIZE`，块边界保留 `CHUNK_OVERLAP` 重叠。

**参数不是拍的，是消融出来的**（6 题 60 分制，贪心/累积消融——每步锁定当前最优再消融下一个）：

| 阶段 | 配置 | 得分/60 |
|------|------|--------|
| ① 分块大小（重叠 50 固定） | **300** 🏆 / 500（基线）/ 800 / 200 / 1000 | **46** / 44 / 32 / 30 / 30 |
| ② 重叠窗口（块 300 固定） | **50** 🏆 / 30 / 60 / 90 / 120 | **46** / 42 / 36 / 24 / 8 |
| ③ top_k（300/50 固定） | **8** 🏆 / 3 / 5 | **46** / 22 / 0（疑似测试事故，待重测） |
| ④ 温度（300/50/8 固定） | **0.3** 🏆 / 0.4 / 0.2 / 0.1 / 1.0 | **46** / 36 / 30 / 28 / 12 |

**四条结论**：

1. **中偏小块最优**（300 > 500 > 800≈200≈1000）：小块语义更细、信息密度高，
   配合多取（`top_k=8`）能拼出完整答案
2. **重叠窗口「越大越崩」**（50 → 120 得分 46 → 8）：小块 + 大 overlap →
   块间大量重复 → 信噪比断崖下降。**这条跟直觉相反**，很多教程说 overlap 越大越安全
3. **`top_k` 与块大小强耦合**：小块需要多取补全信息，8 是 300 字块的甜点
4. **温度 0.3 是甜点**：0.1~0.4 区间内 0.3 是峰值；1.0 全开时数字题崩盘（12 分）

后续在**全量库**（1195 篇）上又跑了一轮三阶段消融（12 组合粗网格 → 7 组合细网格 → `top_k`），
结论不变。参数已同步进 `.env.example` 与 `campus_scraper/pipeline.py`。

**消融纪律**：一次只改一个参数，用同一组问题对比；每次重建会**清空** ChromaDB；
对话日志按 `EXPERIMENT_TAG` 分文件，每条记录自动附带当前模型/温度/上限/`top_k`。

### 7. 文档解析：表格结构化 + OCR 兜底

| 格式 | 处理 |
|---|---|
| TXT / MD | 直读 |
| DOCX | `python-docx`，段落 + 表格 |
| HTML | BeautifulSoup + lxml（爬虫链路） |
| PDF 正文 | `pypdf` 提取线性文本 |
| **PDF 表格** | `pdfplumber` 结构化提取，每行展开为 `单元格 \| 单元格 \| …`，用 `【表格N】` 标记插入正文 |
| **扫描件 / 图片型页** | 提取不到文本的页 → 渲染成图 → **RapidOCR 中文识别**，标记 `【OCR识别·第N页】` |

> 为什么加表格和 OCR：校园通知里**大量关键信息在表格中**（分数线、时间安排、名单），
> `pypdf` 只提取线性文本会把表格拍平成一串无结构字符，答案里的数字就对不上了。
> 而学校历史通知有不少是**扫描件**，没有文本层。OCR 引擎**懒加载**（首次遇到才加载）。

上传白名单：`.txt / .md / .pdf / .docx`。

### 8. 多轮记忆与查询缓存

| | 多轮记忆 | 查询缓存 |
|---|---|---|
| 存储 | Redis | Redis |
| key | `chat:history:{session_id}` | `rag:answer:v2:{sha1(规范化问题)[:16]}` |
| 结构 | `LPUSH` 列表 + `LRANGE` | `SETEX` JSON（answer + sources + thinking） |
| TTL | **1800s（30 分钟）** | `QUERY_CACHE_TTL`，默认 **3600s** |
| 降级 | Redis 挂了 → 静默降级为**前端传来的会话历史** | 读失败返回 `None` → 直接检索 |

**缓存 key 的取舍**：`_cache_key` 只规范化 message、**忽略 history**。
理由是校园问答的问题**独立性高**（「报名截止时间」就是那个答案），命中率优先。
代价是同一问题在不同上下文下会拿到同一个缓存答案——对这个场景可接受。

**缓存失效**：知识库内容变化（上传文档 / 爬虫入库成功）后调 `_flush_query_cache()`，
按前缀 `rag:answer:v2:*` 用 **`scan_iter` 逐一删除**（不用 `KEYS`，避免阻塞 Redis）。

### 9. MCP 工具与安全

**MCP**（`mcp_server/`）暴露 3 个工具，供外部 Agent 调用：

| 工具 | 作用 |
|---|---|
| `search_knowledge_base(query, top_k=5)` | 混合检索，**与聊天链路共用 `app_backend._search_knowledge_base`**，保证外部 Agent 与站内问答行为一致 |
| `list_sources()` | 列出知识库所有文档来源及块数 |
| `ingest_file(file_path)` | 解析 → 切分 → 入库 |

**安全**：

| 措施 | 实现 |
|---|---|
| 接口鉴权 | `X-API-Key` header，用 `hmac.compare_digest` **恒时比较**（防时序侧信道） |
| 输入校验 | 历史条数 / 总字数上限（`MAX_HISTORY_TURNS=10` / `MAX_HISTORY_CHARS=2000`） |
| 上传校验 | 扩展名白名单 |
| 隐私 | 入库前脱敏 + Prompt 层禁止输出个人联系方式 |
| 爬虫 | 限速，不打挂目标站；只爬公开信息 |
| 免责 | 前端标注「个人学习项目，非官方应用」 |

### ⚠️ 关于 60/60：它是单次采样，不是稳定性质

**2026-09-17 用同一份代码跑了两遍，得到 60/60 和 50/60。**

根因：这道题要过**两级 LLM**（回答 + 打分）。某次回答级 LLM 把工具参数写成
`query='招生录取分数'`——**把校名改写掉了**，闸门 A 没东西可拦，检索返回本校分数，
回答里如实列了 52 个三位数字，评分 LLM 按「含基准表外数字即判幻觉」给了 0。
**检索层两次完全一致**，差别只在模型最后那段回答要不要多嘴抄数字。

**这条路径已修**（即上面的闸门 B），修复后连跑 3 次 Q6 全 10/10、总分 60/60。
**但这不能证明修复有效**——那几次 LLM 未必会改写掉校名，而 60/60 本身又有 ±10 分采样噪声。
真正的证据是一个**假 LLM 的端到端测试**：它第一轮必定返回那个丢了校名的 `tool_use`，
**把这次改写钉死，不依赖模型随机性**。

> **结论**：衡量检索层改动**必须用确定性指标**（`eval_guard_probe.py`），**不要用 60/60**。
>
> 25/50/100 题那三套的题库与脚本从未入库、已彻底丢失，无法复跑（成绩仅存于表内）。

## 踩过的坑

### 块 ID 撞车导致整篇文档静默丢失

**现象**：全量 1195 篇入库后块数只有 5507，比预期少了一截，**且不报错**。

**根因**：块 ID 用的是 `sha256(标题)`。而**跨分类有 65 组 / 141 篇同名文档**
（同一通知被发在「通知公告」和「教务处通知」两个栏目），标题相同 → 块 ID 相同 →
**Chroma 后写覆盖前写**，整篇文档没了。

**修法**：块 ID 改为 `sha256(相对文件路径)`；`source` 标签从「文件名 stem」改为
「相对路径（分类/文件名）」——否则补块时同名文档会被当成同一篇。

**效果**：1194 篇全部入库（5919 块），**Q3 的历史 0 分彻底修复**。

> 教训：向量库主键用自然语言里「看起来唯一」的字段（标题）**一定会撞**。

### chroma_db 损坏 + `| tail` 掩盖了 segfault

**现象**：某次消融跑完 segfault 后，**所有**重建都在 `chromadb.api.rust._count()` 崩
（Windows access violation），日志在模型加载后中断。

**排查**：`python -X faulthandler` 定位到 `_count()`；全新临时库 count 正常、
现有库 count 崩 → **现有库的 sqlite/HNSW 索引损坏**。

**修法**：删掉 `chroma_db` 重建。**敢删的理由**：源头 `scraped_docs/` 完好，
**向量库是可再生的派生数据**。

> 两条教训：① **`| tail` 会掩盖 segfault 的退出码**（假 `exit=0`），
> 排查崩溃必须直接取 python 退出码或用 faulthandler；② **派生数据要能和源数据分离**，
> 才敢在损坏时直接重建。

### 嵌入模型每次加载都发 HTTP 校验

`sentence-transformers` 每次加载模型都去 `hf-mirror.com` 校验，网络异常时**加载挂起甚至
segfault**。修法：加 `HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1`，加载降到 <3 秒。

### 重排把召回截断掉了

加了重排后 Q5 检索级命中从 4/4 **掉到 0/4**——`RERANK_TOP_N=8` 时重排把补块带进来的
关键句**截断挤掉了**。改为 `N=16` 后恢复。

> 普适结论：**重排是「排序」组件，不该承担「截断」职责**，截断预算要留给召回层。

### 可观测性缺口：流式路径的 `add_step` 没有 `yield`

排查 Q6 时**无法判断**走了哪个闸门分支。根因是工具返回后的 `add_step(...)`
只 append 进 `thinking_steps`、**没有 `yield ThinkingEvent(...)`**——
这些步骤在流式过程中客户端根本看不到，**评测回放里也查不出走了哪个分支**；
而非流式的 `run()` 是会下发的，**两处行为不一致**。已统一补上 `yield`。

## 已知局限

| 局限 | 说明 |
|---|---|
| 判官判**相关性** ≠ **可答性** | 「主题词在库、具体事实不在库」的灰区题（如「现任校长是谁」）会被放行 |
| 重检环默认关 | 消融证明无收益且有反效果（把正确拒答翻成放行），保留可开关 |
| 首句净化只认汉字 | 同轮「英文 + 中文」旁白会漏；实测未遇到 |
| 查询缓存忽略 `history` | 同一问题在不同上下文下共用缓存，是命中率优先的取舍 |
| 隐性时效词不敏感 | 「最近有安排暑期社会实践」的「最近」检索器感知不到，2025 年通知可能排在 2026 年前 |
| 60/60 有 ±10 采样噪声 | 两级 LLM，见上文 |
| 25/50/100 题题库已丢失 | 从未入库，无法复跑 |

**「隐性时效词」这条评估过、决定不做**，理由三条：① 显式年份已可用
（`_extract_year` + `where={"year": ...}` 的 ±1 年窗口），缺的只是「最近 / 今年」这类
**隐性**时效词；② 失败形态是「偶发用错年份」的质量瑕疵，不是归属错误，
而它要改**检索排序**，得重跑消融、可能拖累基准；③ 原先设想的方案
（加权 / 过滤最新年份）**本身不成熟**——「去年的心理健康工作」就该往旧了查，
无脑提权最新年是错的。真要做，得先做**时间词识别**，那是**新功能**不是修 bug。
